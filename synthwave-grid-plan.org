* Intent and current recommendation
Improve the existing outrun grid using the supplied scene as visual inspiration. Consider performance, download/startup speed, integration effort and future refactoring before choosing a renderer. Three.js is permitted in principle; it is NOT prohibited by this plan or by the user's requirements.

Recommendation: implement a bounded CSS improvement for the existing fixed-camera background. Separate the stationary projection/fade from the travelling grid, refine perspective, and add restrained horizon haze/glow. Preserve both theme palettes and the existing preferences. This recommendation follows the current feature scope, not an unperformed benchmark or a claim that CSS always performs better.

Three.js remains a real alternative if rendered bloom, camera movement or depth-aware scene effects become essential. Do not implement all alternatives merely to compare them. Do not silently add a renderer if CSS visual review falls short: refine this same plan with a bounded, authorized renderer experiment and measurable acceptance criteria.

This is a planning handoff, not an implementation or dependency authorization. Only this project-root document was manually edited. The continuation performs read-only Git inspection and repository checks; results are recorded separately from pending implementation gates. No grid implementation or renderer benchmark has been performed. * Renderer decision
** Options considered
| Option | Visual benefit/limit | Delivery and runtime | Integration/refactoring cost |
|--------+----------------------+----------------------+------------------------------|
| A: CSS stationary plane + travelling texture | Convincing fixed-view perspective, smooth travel, gradient haze and glow approximation; not true bloom or scene fog | No new rendering JS library; larger painted/composited layers can still cost GPU memory and frame time | Small shared styles/two-markup change; existing CSS fallback, SSR, theme and motion behavior remain |
| B: lazy Three grid, no composer | Real camera geometry and distance fog; additive grid, but no post-process bloom | Additional download/parse/GPU initialization and persistent rendering; DPR-sensitive | Client-only loader, lifecycle, resize/DPR, settings synchronization, disposal, failure fallback and additional tests |
| C: Three + composer + bloom | Closest to reference luminosity and camera/depth effects | B plus post-processing code, render targets, multiple passes and extra GPU memory/fill rate | Highest maintenance burden, transparency/color-space validation, fallback and device coverage |

No option has been measured here. Lazy loading changes when cost is paid; it does not remove the cost. Wallpaper loads immediately for skip-boot users, and automatic post-boot chunks still count toward route totals. CSS is not declared the fastest in all cases. Option B may deliver little additional value over A for this fixed-camera scene while still adding most renderer lifecycle responsibilities. Option C is appropriate to evaluate if actual bloom becomes a requirement.

** Reference-specific observations
- Borrow the perspective/fog illusion, brighter horizon band, soft line glow and repeating forward travel; do not transplant the sample's whole screen overlay/UI or numeric settings as a design specification.
- =distance = speed * delta * 60= is reference-60fps speed normalization, not inherently frame-rate-dependent. A later renderer should document world-units/second and reset/clamp elapsed time after suspension so returning to a tab does not leap forward.
- Modulo-offsetting a finite GridHelper does not make its edges infinite. Its two-row cycle can repeat a texture but does not prove coverage at all viewports/camera angles. Do not copy that claim untested.
- The sample starts RAF and listeners without returning a cancellation/disposal lifecycle. It lacks explicit reduced-motion, hidden-tab, context-loss and load-failure handling. Its post-process alpha behavior must be tested; repeatedly clearing alpha alone does not prove transparent output from every pass.
- DPR is capped at 2 initially, but resize only updates sizes/aspect. Moving between displays and post-processing buffer DPR need deliberate handling. A cap of 2 is not itself a mobile performance guarantee.
- The sample's initial bloom strength is overwritten during rendering. Use one authoritative setting if eventually adopting bloom, rather than copying conflicting constants. No reference source license was supplied; use concepts, not verbatim source with assumed licensing.

** Decisions versus assumptions
- Decision: recommend A now; no Three dependency or trial is scheduled. Three remains available after an explicit scope refinement, ADR and authorization for manifest/lockfile changes.
- Decision: preserve cyan/light and magenta/dark, current sky/sun/mountains, CRT controls and boot timing. The inspiration is not a request for all-cyan themes or a new bloom checkbox/speed slider.
- Decision: one vertical implementation section, one writable source owner; mockup, production effect and tests belong to the same bounded slice. Review/verification are gates within it, not artificial follow-up feature sections.
- Assumption: a convincing fixed-camera approximation is sufficient. No requirement for camera interaction or physically rendered bloom was stated. If that changes, reconsider A before implementation rather than forcing it.
- Assumption: CSS geometry can cover supported viewports with a bounded texture. Actual projected coverage and mobile performance must be demonstrated.
- Open measurements: current and changed route bytes, compositor/raster cost, mobile frame behavior and visual adequacy. None is an established success or blocker yet.

* Design and compatibility contract
** Stationary projection and moving texture
At both existing Svelte call sites add one decorative =.outrun-grid-plane= wrapper around the existing =.outrun-grid=. The wrapper owns fixed perspective/rotation, clipping, mask and floor placement. The child owns the repeating gradients and ONLY local translateY travel. Keep =.outrun-grid= as the animated DOM element so existing preference tests remain meaningful. The horizon stays a stationary sibling below content in the current stacking hierarchy.

Use one =--grid-row-step= for both gradient repetition and endpoint translation. Start with the existing 26px pitch; tune geometry against captures, not guessed Three camera equivalents. Overscan the child by at least the travel distance and account for projected viewport edges. A repeated texture must cover the clip at 0, half-cycle and the exact endpoint; numerical pitch equality alone is not proof of visible seamlessness. Projection and fade must not move with phase.

Do not animate background-position, blur, filter, gradient parameters or geometry/layout. Use a bounded static gradient/horizon shadow for haze/glow; do not add full-screen mix-blend-mode above windows or icons. A third animated production layer or a reusable rendering framework is not needed for this slice.

** Token seam
New names below are proposed CSS-private contracts, not claims of existing APIs:
- =--grid-row-step=: one repetition/travel length; initially 26px.
- =--grid-line-color=: derived from existing cyan/light and magenta/dark tokens.
- =--grid-haze-color=: derived theme color for bounded horizon atmosphere.
- =--grid-horizon-shadow=: theme-appropriate static glow declaration.
Reuse existing =--grid-scroll-duration= and local =--grid-perspective= / =--grid-rotate=. Put new production values in =src/styles/tokens.css= first, then consume in effects. Reuse existing palette tokens instead of introducing raw reference hex values. In the standalone mockup, mirror only needed token values in its existing root/theme token blocks; do not import production CSS or add a build system. No general token cleanup.

** Mockup seam
Refine =retro-os/styles.css= first, using the existing =.wallpaper-grid= as the stationary plane and a =::before= texture if needed. Its existing =.wallpaper-haze= handles reference atmosphere. The reference need not acquire a splash or reproduce Svelte DOM. Preserve its flat-wallpaper toggle and reduced-motion behavior. Inspect the reference before translating the visual changes to production. If the existing markup cannot express the design, stop for a path/scope update rather than opportunistically editing =desktop.jsx=.

** Unchanged public interfaces
- =GridSpeed = "paused" | "slow" | "normal" | "fast"=, storage key =retro-os:settings=, settings parser/bootstrap/store and four root appearance attributes remain unchanged.
- Normal/slow/fast remain 8s/16s/4s, and paused freezes the animated child. Reduced-motion retains the existing near-zero-duration/one-iteration contract and a static visible floor.
- Wallpaper remains decorative =aria-hidden=; added splash decoration is also hidden without hiding its role=status content. Decoration is pointer-transparent and not focusable.
- No new island, route, public TS API, dependency, asset download, timer/RAF, settings UI or boot delay. Do not modify =Wallpaper.astro= (not the active shell import), the settings store, or unrelated effects.
